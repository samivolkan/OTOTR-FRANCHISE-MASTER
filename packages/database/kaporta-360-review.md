# Kaporta 360 — additive pilot review

2026-09-06. Requested scope: make the photographic demo usable with assigned ERP work orders, evidence, technical review and gated customer reports.

Reviewed sequence: `reviewed-migrations/20260906101627_kaporta_360_pilot.sql`, then `reviewed-migrations/20260906110018_kaporta_360_technician_write_guard.sql`. Canonical CLI-generated migrations of the same names live in `supabase/migrations`. Each pair must have identical SHA-256 before application. Only these migrations are in this execution set; unrelated/unreviewed migrations are excluded. The second change explicitly restricts preparation to INSPECTION_TECHNICIAN / TECHNICAL_SUPERVISOR, preserving the ERP branch-manager technical-data read-only rule even if a manager is set as task owner.

Target verified through the Supabase connector: project `bsjkohwbtrfwrqcyhsfz`, displayed name **ototr-staging**, PostgreSQL 17.6.1. No existing customer rows were used for fixtures. Current table columns, role/check constraints, ownership RPC signature, pgcrypto schema and storage policies were read before implementation; these are more recent than the June role draft.

- Creates five `k360_*` tables, a non-exposed helper schema, authenticated RPCs, a server-only share resolver and a private `kaporta-360` storage bucket. Existing case/task/report schemas and RPCs are not replaced.
- All five tables use RLS. Authenticated users have SELECT only on sessions/photos, subject to case scope; no direct mutations. Reports, share hashes and audit events have no client table grants. All mutation is validated through RPCs; SECURITY DEFINER functions use an empty search path and database-backed active identity.
- Write requires the same branch, `BODY_PAINT_CHECKUP` ownership, task OPEN, unlocked case in TECHNICAL_ENTRY_OPEN or REVISION_REQUESTED, and a draft/returned session. Owner reassignment is re-evaluated for every operation. Session revision checks prevent silently overwriting another editor; session/case/task row locks serialize relevant decisions. Existing claim/reassignment/return mechanisms remain authoritative.
- Review requires branch TECHNICAL_SUPERVISOR/BRANCH_MANAGER or global CEO/GENERAL_MANAGER. Anyone who prepared or edited this capture cannot approve it. This is a module-specific approval; it neither completes ERP tasks nor approves the final ERP report.
- Photos cannot be overwritten or deleted by clients, even with another permissive storage policy. Object path, persisted Storage metadata, dimensions, MIME, count, supplied SHA and duplicate registration are checked. Image dimensions, hash and capture time are client declarations; they are not forensic server-side verification. A technical reviewer must check actual image quality and identity.
- Required capture set: 24 ring slots plus 4 upper slots. Non-original work or a defect needs a detail photo and at least five characters of explanation. Metal inspection needs three readings; no automatic classification from microns. Evidence belongs to the session, annotations are normalized and bounded.
- Sharing needs module approval, approved/delivered locked ERP case, report_approved_at, matching case revision and a LOCKED final_report of that revision. The 256-bit token is stored only as SHA-256; it expires after seven days. Only the server role can resolve it, and gates are rechecked on every access. Returns/revocation invalidate links. Photo URLs last 120 seconds.

Validation: `npm test` in `apps/web/vehicle-3d` runs the exact SQL on PGlite/PostgreSQL with pgcrypto, real roles, RLS, deliberately permissive legacy storage policies and synthetic case/task records. Covered: cross-branch/anonymous access, direct update denial, ownership transfer, start-evidence gate, revision conflicts, all 28 angles, original registration, idempotence, detail/measurement requirements, foreign references and annotation bounds, review freeze, self-approval rejection, independent approval, final-report lock/version gates, revocation and inactive users. The customer function is tested separately for token validation, origin allowlist, snapshot-only signing and removal of internal identifiers.

Rollback is non-destructive: remove the pilot entry, stop new writes by revoking authenticated execution of `k360_open` and `k360_command`, and disable the customer edge endpoint. Retain all recorded evidence/audit tables and private objects. No DROP/TRUNCATE/data deletion is part of rollback. Before any production rollout, run physical Android/iOS capture and review a real authorized vehicle with separate technician/reviewer accounts.

## Deployment verification

The first migration and customer endpoint were applied to the verified staging project. Metadata checks confirmed all five RLS flags, a private bucket, no anonymous work RPC execution, no authenticated share-resolver execution, no direct authenticated writes and an empty sessions table. Public HTTP checks confirmed anonymous RPC 401, nonexistent capability 404, allowed CORS 204 and unexpected origin 403. No real inspection was created for testing.

Security advisor review: five [authenticated SECURITY DEFINER warnings](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable) are intentional for guarded work RPCs; they validate identity, scope, ownership, state and revision before touching otherwise inaccessible tables. Three [RLS with no policy notices](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) are intentional deny-all client access for immutable reports, share hashes and audit rows, which also have no client grants. No new missing-RLS or anonymous-executable finding. New-index unused notices are expected for empty pilot tables. Existing project findings are outside this change and are not reported as fixed.
